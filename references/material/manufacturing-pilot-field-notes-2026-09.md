# 候选素材 · 一个 200 人层制造企业试点的一阶段怎么打（2026-09）

> 整理日期:2026-09-14。素材层,供课程维护者评审;未进入讲义、诊断评分、学生端或托管站。
> 来源:一支驻场 FDE 团队在国内一家医疗器械制造企业的 AI 应用一阶段试点(2026-08 进场,覆盖研发 / 产品 / 项目 / 采购四个部门,合同周期约两个月)。**截至整理日项目仍在进行,验收未完成,本文只写已经发生的判断和做法,不写结果。** 公司、人名、金额、合同条款原文一律不出现;涉及客户内部人物只写岗位。

## 为什么值得补进 School

九宫格第二层(约 200 人、进步型)在现有讲义里只有一个车队案例。这是第二个第二层案例,而且是制造业、多部门、有正式合同的一阶段。它回答的是一个学生学完九宫格后一定会问、但讲义没答的问题:**签下第二层的"一阶段"合同之后,头两个月到底该做什么、不做什么。**

## 一、一阶段的定位:调研 + 基线 + 可视化成果,为二阶段做漏斗

进场前团队内部先钉死一件事:一阶段不解决这家公司十年积累的组织问题。它的产出是三样——把四个部门的真实工作流摸清(调研)、把"现在多慢、卡在哪"量出来(基线)、做出一两件管理层此前看不到的东西(可视化成果)。二阶段签单的判断被拆成三份:一半靠"管理层看不到的任务级可视化",三成靠信任关系,两成靠二阶段方案画出的图景。

这和九宫格 ④「共同定义试点 → 分阶段路线图」是同一件事,增量在于:**第二层老板不为省钱,但一阶段仍然要有一件他亲眼看到的东西,否则"进步"没有抓手。**

## 二、三条线:合同线、糖果线、沉淀线

团队把工作分成三条线,并且**只跟客户的项目接口人对齐第一条**:

- **合同线**:合同写明的七项交付物按最小口径逐项交付,只有一项(部门基线报告)刻意做厚。
- **糖果线**:合同之外、汇报时才亮出来的加分项(例如从采购周报还原出的任务级甘特图、生产计划的作战图)。平时不承诺,汇报才亮。
- **沉淀线**:方法、脚本、bot 配置这些内部资产,对外不提。

教学价值:学生常见的错误是把糖果线当合同线承诺出去,或者把沉淀线拿去跟客户邀功。三条线分开,才有"对内标准化、对外 100 分定制"的空间。

## 三、基线口径:三类基线分开算,量表折算不能冒充实测

基线是一阶段做厚的那一项。团队定了一份口径文件,核心是三类基线**分别**建立、**不能**互相替代:

| 基线 | 回答的问题 | 责任人 |
|---|---|---|
| 项目关键路径基线 | 哪些任务、依赖和阻塞真正决定里程碑 | 项目经理整合,各部门确认本部门节点 |
| 部门工作基线 | 人力投在哪、产出结构、瓶颈 | 部门负责人 |
| 个人任务基线 | 一项任务过去怎么做、投入多少、AI 可能怎么参与 | 员工填真实样本,负责人校准 |

几条纪律直接可教:

- **劳动时间与等待历时分开记**。任务省时只有在消除关键路径上的真实阻塞之后,才能推断项目周期改善。
- **量表折算出来的小时数必须标明"量表折算",不能冒充计时实测**;区间不压成精确值。
- **没有测量覆盖率和专业验收证据,不报告个人、部门或公司整体提效**。向管理层报告时,任务节省率、覆盖率、标准工时释放率、关键路径影响要同时给。
- **不做个人排名**,基线服务于试点选择和前后对比,不用于绩效。

这是一号位沟通第 3 课「成功指标 / 停止条件」在制造业现场的具体形态。

## 四、样板工作流就是周报本身

团队没有先做一个新工具,而是把合同里"IM 样板工作流"这一项定成:**周报本身**——固定时间发、固定时间收、收完自动同步回 FDE 团队自己的协作空间。选周报的理由是它已经存在、每周必发、没人能说"我们不用"。

在它之上长出的第一个杠杆样板:把采购部的历史周报还原成任务级甘特图,把每条阻塞点还原到原文证据。标准是一句话:**信息只搬运一次**——员工写一次周报,管理层就该看到任务级进度,不需要第二次填报。这就是"管理层看不到的任务级可视化"。

## 五、员工调研 bot:代写周报型,不是问卷型

客户此前做过员工调研,员工敷衍有前科。团队的做法:

1. bot 做成"帮你把这周工作整理成周报"的形态,而不是"请回答以下问题";一次只问一个问题,员工说"这周没新增"也是有效事实。
2. 老板出面站台,两周内覆盖全员,催收进日历。
3. 按部门和岗位路由三种访谈:通用、部门侧重(如采购只问增量与阻塞,不重新盘问"采购平时做什么")、以及给已经在用 Coding Agent 的软件 / 算法岗一种 A2A 模式——bot 发一段提示词,员工自己的 agent 扫描本机近期工作,整理成结构化摘要以员工本人身份发回。
4. 报告只记工作事实,**不生成绩效、排名、忙闲或能力评价**;员工侧收口只有一段文字小结和致谢,不发报告。

## 六、几条敏感线(通用化写法)

- 技术负责人内向、重技术,由一名 FDE 单线维护,不硬压,不越过他直接找他的下属。老板很在意这个人的情绪。
- 采购对外沟通涉及商务敏感,一律不采集聊天记录与录音,只用周报和流程文件。
- 客户的口径是"加项目不加人",不是裁员降本;所有价值表述跟着这个口径走(与现场素材里那位厂长的回答同一条线)。
- 不碰光学 / 结构 / 机械核心设计,AI 只在文档、资料查询、跨部门协同和重复操作上落地。

## 七、验收线的设计:部门认可作我方验收线,正式签字不揽

合同要求基线报告由部门负责人签字。团队把"部门认可"(录音 + IM 留痕)定为**自己**的验收线,正式签字由老板组织、团队不主动揽。同理,MRP 类工具不跟岗辅导、早交付 V0 换来 PMC 的基线核对;中期汇报不排;计划只排到长假前,假后再定。原则是:**把自己的验收线放在自己能控制的证据上,把仪式性动作留给客户。**

## 八、团队自己怎么协作

四部门并行、多名 FDE 加多个 agent 同时干活,团队用一个私有仓库做全量透明存档,只维护三份文件:任务看板(ID / 目标 / 主责 / 输入 / 允许修改的文件 / 产出 / 确认人 / 状态)、决策记录(只记影响多个任务或目录的决定)、交接模板(完成了什么 / 改了哪些文件 / 依据 / 验证 / 剩余问题)。三条纪律:一个文件同一时间只有一个主责;原始逐字稿只追加勘误不改写;仓库里的"已完成"不等于项目验收。

这套模板已脱敏开源(见 `HA7CH/ai-native-company` PR #13 的 `vault-templates/collab/`),共修 GitHub 课可以直接引用。
