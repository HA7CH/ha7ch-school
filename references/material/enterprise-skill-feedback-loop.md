## 一、值得补进 School 的判断

企业 Skill 的价值同时包含两部分：首次让工作可执行，以及在持续使用中把人的纠正吸收到下一次执行。交付一个文件或插件只完成了前一部分。

现有现场素材已介绍 Context → knowledge → Skill → distributed Skill 的组织回路。本素材聚焦一个更小的交付问题：**一次业务纠正，怎样变成值得分发给其他使用者的规则？**

稳定的方法会随现场证据改进；临时偏好、某个客户的特例和一次误操作则需要保留适用范围。改进目标不是让规则越来越多，而是减少同类错误，同时不破坏原来正确的工作。

## 二、教学转化建议：让一次纠正走完六个动作

以下是本次编写的教学设计，基于上述判断展开，**不是对某篇口播的逐句还原，也不是已经验证的客户 SOP**。

1. **留证据**：记录任务、错误结果、人工纠正和预期结果；敏感输入留在受控环境，不把原件搬进公开 Skill。
2. **找原因**：先区分信息缺失、工具失败、权限不足与规则缺失。工具不可用不能靠多写一条提示词掩盖。
3. **定范围**：说明纠正适用于谁、哪类输入、哪些例外。单一对象的特例进入局部配置，不直接升级成全员规则。
4. **改最小一处**：修改真正导致错误的说明或流程；不顺带更换整套方法。
5. **回放验证**：同时检查原来失败的样例、原来正确的样例和不该执行的越权样例。保留未解决的失败，不只展示成功截图。
6. **审查与分发**：由有权负责的人确认改动范围，记录版本和退回方式，再核验使用者实际收到的版本。合并 PR 只证明代码合入，不能代替使用者端的验证。

这六步让“持续改进”成为可以验收的工作，而不是一句泛泛的能力宣称。

## 三、可选练习：修正一次错误，而不是重写整个 Skill

**以下为合成教学情境，不对应任何真实客户。**

一个内部资料助手拿旧版规则回答了问题。业务负责人给出纠正后，开发者准备把这句话直接追加到所有人的 Skill 中。

维护者可让学生先观察三个事实：原问题是否提供了适用日期；助手是否能读取当前有效规则；业务负责人的纠正是否只适用于某一项目。随后用一个最小修复演示：明确有效版本的选择方法和无法确认时的停止条件，把项目特例留在项目范围。

建议提交物：

- 一段原因判断，标明已知与待确认；
- 最小规则 diff，并说明适用范围；
- 三个回放用例：原失败、原成功、信息不足时停止；
- 审查人、版本与使用端核验记录的空白模板。

学生无法证明原因时，合格动作是保留不确定性并补证据；不能为了交作业编出成功结果。上述项目是练习验收建议，**不改变现有 FDE 诊断评分表**。
